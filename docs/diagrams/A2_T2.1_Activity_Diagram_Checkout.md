## 3. Cấu trúc Swimlane và Phân tách Độc lập giữa Return URL và IPN/Scheduler (`R-03`)

Sơ đồ được chia thành **5 swimlane** phản ánh đúng kiến trúc thực tế của BrewLite:

1. **`Customer` (Actor chính):**
   - Mở giỏ hàng, nhập mã giảm giá (tùy chọn) và kích hoạt Checkout.
   - Xác nhận thanh toán (hoặc chọn Retry khi đơn ở trạng thái `PAYMENT_FAILED` còn trong hạn `E`).
   - Thực hiện thanh toán, hủy giao dịch hoặc đóng trình duyệt trên cổng `VNPay Sandbox`.
   - Nhận kết quả cuối cùng trên giao diện Checkout cho **mọi nhánh thanh toán** (`VNPay`, `ZERO_AMOUNT`, `Mock`).
2. **`Next.js Frontend` (Thành phần giao diện / Client):**
   - Kiểm tra phiên đăng nhập/JWT phía client trước khi gửi `POST /orders`.
   - Giữ nguyên giỏ hàng client-side khi tạo Order `PENDING` (chỉ xóa giỏ khi đã xác nhận `Order == PAID`).
   - Sinh `Idempotency-Key` (8..64 ký tự) và điều phối gọi API thanh toán.
   - Trên nhánh VNPay: Chuyển hướng trình duyệt sang `VNPay Sandbox`; tiếp nhận `Return URL` (`EF-11`: không tự coi Return URL là `PAID`) và gọi `GET /orders/me` (bounded polling) để đọc trạng thái từ Database.
3. **`NestJS Backend` (Thành phần xử lý nghiệp vụ & API):**
   - Thực thi `JwtAuthGuard`, `ValidationPipe`, `MockPaymentGuard`, kiểm tra quyền sở hữu (`ownership`), tính giá authoritative, kiểm tra `Idempotency-Key` và điều kiện 1 Order active (`BR-C02`).
   - Xử lý độc lập ở nền qua webhook `GET /payments/vnpay/ipn` hoặc qua chu kỳ `PaymentReconciliationScheduler` / `VnpayQuerydrService` / `OrderExpirationService`.
4. **`PostgreSQL DB` (Thành phần lưu trữ dữ liệu giao dịch):**
   - Đảm bảo tính nguyên tử (ACID transaction) và khóa bản ghi theo thứ tự chuẩn (`BR-C05`) khi tạo `Order`, giữ/tiêu thụ/hoàn trả tồn kho & coupon, cập nhật `Payment` và cộng điểm tích lũy.
5. **`VNPay Sandbox` (Actor ngoài hỗ trợ trên nhánh VNPay):**
   - Hiển thị cổng thanh toán Sandbox và kích hoạt hai luồng độc lập (`fork ... end merge`):
     - **Luồng 1 (Browser Redirect — độc lập với IPN):** Nếu trình duyệt quay về `Return URL` (`Có`), `Next.js Frontend` gọi `GET /orders/me`; nếu khách đóng trình duyệt (`Không`), phiên trình duyệt có thể kết thúc ngay (`stop`) hoặc khách mở lại trang Đơn hàng sau đó mà **không cản trở Backend xử lý đơn**.
     - **Luồng 2 (Server-to-Server IPN / Scheduler — độc lập với trình duyệt):** Chạy độc lập ở nền giữa `VNPay Sandbox / Scheduler`, `NestJS Backend` và `PostgreSQL DB`, kết thúc (`stop`) ngay sau khi commit kết cục cuối vào Database mà **không cần đồng bộ (no Join Bar)** với trình duyệt Return URL.

## 4. Danh mục các Decision Node và Chu kỳ Scheduler (`R-02`, `R-04`)

Tất cả các Decision Node trong cả 4 file PlantUML đều tuân thủ quy tắc thống nhất: **nhánh `then` luôn mang nhãn khẳng định `Có (...)` khớp trực tiếp với câu hỏi nghi vấn trong hình thoi, và nhánh `else` luôn mang nhãn phủ định `Không (...)`**.

| # | Decision Node (Câu hỏi tại hình thoi) | Nhánh `then (Có...)` | Nhánh `else (Không...)` |
|---|---|---|---|
| **D1** | `Đã đăng nhập?` | `Có` $\rightarrow$ Gửi `POST /orders` kèm Bearer JWT | `Không [EF-01]` $\rightarrow$ Yêu cầu đăng nhập, giữ giỏ client (`stop`) |
| **D2** | `JWT & DTO hợp lệ?` | `Có` $\rightarrow$ Bắt đầu DB Transaction tạo Order | `Không [EF-01, EF-03]` $\rightarrow$ Trả `401` hoặc `400 VALIDATION_ERROR / INVALID_CART` (`stop`) |
| **D3** | `Đã có Order active?` | `Có [EF-05, BR-C02]` $\rightarrow$ Rollback & trả `409 PENDING_ORDER_EXISTS` (`stop`) | `Không` $\rightarrow$ Tiếp tục kiểm tra tồn kho & mã Coupon |
| **D4** | `Đủ stock & Coupon hợp lệ?` | `Có` $\rightarrow$ Tính giá authoritative & tạo Order `PENDING` | `Không [EF-04, EF-15]` $\rightarrow$ Rollback nguyên tử & trả `409 INSUFFICIENT_STOCK` / `400` / `409` (`stop`) |
| **D5** | `Đủ điều kiện thanh toán?` | `Có` $\rightarrow$ Tiếp tục phân nhánh theo phương thức thanh toán | `Không [EF-02, EF-06..09]` $\rightarrow$ Trả `404 NOT_FOUND` hoặc `409 Conflict` (`stop`) |
| **D6** | `Đơn hàng 0đ (totalVnd == 0)?` | `Có [AF-03, BR-C07]` $\rightarrow$ `POST /payments/zero-amount` $\rightarrow$ DB commit `PAID` $\rightarrow$ Frontend $\rightarrow$ Customer | `Không: totalVnd > 0` $\rightarrow$ Xét chế độ Mock / VNPay |
| **D7** | `Dùng chế độ Mock [AF-04]?` | `Có: POST /payments` $\rightarrow$ Kiểm tra cấu hình cho phép Mock | `Không: VNPay Sandbox [Main Flow]` $\rightarrow$ `POST /payments/vnpay/initiate` |
| **D8** | `Cho phép chạy Mock?` | `Có [MOCK_PAYMENT_ENABLED]` $\rightarrow$ Xét kết quả thẻ/ví giả lập | `Không [BR-C09]` $\rightarrow$ Trả `403 MOCK_PAYMENT_DISABLED` (`stop`) |
| **D9** | `Thẻ 0002 / Ví 0000 từ chối?` | `Có: Giả lập từ chối` $\rightarrow$ DB commit `PAYMENT_FAILED` $\rightarrow$ Frontend $\rightarrow$ Customer | `Không: Thẻ / Ví hợp lệ` $\rightarrow$ DB commit `PAID` $\rightarrow$ Frontend $\rightarrow$ Customer |
| **D10** | `Hoàn tất đồng bộ ở Pha 1?` | `Có [ZERO_AMOUNT / Mock]` $\rightarrow$ Nhận trực tiếp kết quả `PAID` / `PAYMENT_FAILED` | `Không [VNPay PENDING]` $\rightarrow$ Redirect trình duyệt sang `VNPay Sandbox` |
| **D11** | `Trình duyệt quay về Return URL?` | `Có` $\rightarrow$ Nhận Return URL (`EF-11`), gọi `GET /orders/me` | `Không: Đóng trình duyệt` $\rightarrow$ Xét D12 (`Khách mở lại trang Đơn hàng?`) |
| **D12** | `Khách mở lại trang Đơn hàng?` | `Có` $\rightarrow$ Mở lại trang chi tiết/xác nhận, gọi `GET /orders/me` | `Không` $\rightarrow$ Kết thúc luồng trình duyệt (`stop`), Backend vẫn xử lý ở Luồng 2 |
| **D13** | `VNPay gửi được IPN?` / `Nhận được webhook IPN từ VNPay?` | `Có: GET /payments/vnpay/ipn` $\rightarrow$ Kiểm tra chữ ký HMAC-SHA512 & số tiền | `Không: Mất IPN / Timeout [AF-06, EF-14]` $\rightarrow$ Scheduler kích hoạt đối soát nội bộ (`QueryDR` / `OrderExpiration`) |
| **D14** | `Chữ ký & số tiền hợp lệ?` | `Có` $\rightarrow$ Chấp nhận bằng chứng IPN, vào vòng lặp Finalization | `Không [EF-10]` $\rightarrow$ Từ chối Finalization, giữ nguyên DB, trả RspCode lỗi (`stop`) |
| **D15** | `Kết quả giao dịch là SUCCESS [00]?` | `Có: SUCCESS [00]` $\rightarrow$ Xét D16 (`Đúng hạn paidAt <= E & chưa hủy?`) | `Không: FAILED / UNKNOWN` $\rightarrow$ Xét D17 (`Kết quả là Terminal FAILED?`) |
| **D16** | `Đúng hạn (paidAt <= E) & chưa hủy?` | `Có [Main Flow]` $\rightarrow$ Xác định `Payment = SUCCESS`, `Order = PAID` (`break` $\rightarrow$ Commit DB) | `Không: Đến trễ [EF-12]` $\rightarrow$ Ghi nhận `hasFinancialException = true`, `REQUIRES_REVIEW` (`break` $\rightarrow$ Commit DB) |
| **D17** | `Kết quả là Terminal FAILED?` | `Có [AF-05]` $\rightarrow$ Xét D18 (`Còn hạn TTL 15 phút (now < E)?`) | `Không: UNKNOWN [AF-06..09]` $\rightarrow$ Xét D19 (`Đã tới mốc TTL 15 phút (now >= E)?`) |
| **D18** | `Còn hạn TTL 15 phút (now < E)?` | `Có [AF-05, BR-C04]` $\rightarrow$ `Payment = FAILED`, `Order = PAYMENT_FAILED` (`break` $\rightarrow$ Commit DB) | `Không: now >= E [AF-08]` $\rightarrow$ `Payment = FAILED`, `Order = CANCELLED` (`break` $\rightarrow$ Commit DB) |
| **D19** | `Đã tới mốc TTL 15 phút (now >= E)?` | `Có: now >= E` $\rightarrow$ Xét D20 (`Có VNPay PENDING tạo trước E?`) | `Không: now < E` $\rightarrow$ Giữ `PENDING` $\rightarrow$ **Chờ chu kỳ Scheduler kế tiếp / IPN** |
| **D20** | `Có VNPay PENDING tạo trước E?` | `Có: Vào Grace [AF-07]` $\rightarrow$ Xét D21 (`Đã quá mốc Grace 5 phút (now >= G)?`) | `Không [AF-08]` $\rightarrow$ Hủy đơn tại mốc `E`: `Order -> CANCELLED` (`break` $\rightarrow$ Commit DB) |
| **D21** | `Đã quá mốc Grace 5 phút (now >= G)?` | `Có: now >= G [AF-09, BR-C10]` $\rightarrow$ Hủy đơn sau Grace tại `G`: `Order -> CANCELLED`, `Payment` giữ `PENDING + REQUIRES_REVIEW` (`break` $\rightarrow$ Commit DB) | `Không: E <= now < G` $\rightarrow$ Lưu trạng thái Grace `[E, G)` (`RECONCILING`), chặn tạo attempt mới $\rightarrow$ **Chờ chu kỳ Scheduler kế tiếp / IPN** |
| **D22** | `Vẫn đang PENDING / RECONCILING?` (Điều kiện lặp `repeat while`) | `Có: Tới chu kỳ kế tiếp` $\rightarrow$ Quay lại khóa bản ghi & đánh giá lại ở chu kỳ Scheduler tiếp theo (khi thời gian tiến tới `E` hoặc `G`) | `Không: Đã có kết cục` $\rightarrow$ Thoát vòng lặp & Commit nguyên tử vào `PostgreSQL DB` (`stop`) |

## 5. Đối chiếu tính trung thực với Implementation `A1-final`

1. **Tra cứu trạng thái sau thanh toán (`GET /orders/me` vs `GET /payments/:paymentId/status`):**
   - Trong mã nguồn `A1-final` (`frontend/services/order-confirmation.service.ts` và `backend/src/orders/orders.controller.ts`), việc đồng bộ trạng thái đơn hàng/thanh toán trên trang xác nhận được thực hiện qua route đã triển khai **`GET /orders/me`**.
   - Route `GET /payments/:paymentId/status` có trong đặc tả API Contract v4.0 (`API-03`) và hàm gọi phụ trợ phía client, nhưng **chưa có controller route tương ứng ở backend tại commit `A1-final`**. 2. **Tiến trình đối soát QueryDR (`VnpayQuerydrService` & `PaymentReconciliationScheduler`):**
